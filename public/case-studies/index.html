Case Studies.

A register of every repository we have onboarded with sm refit, start to finish. Each run publishes its whole result: what got genuinely fixed, what was merely baselined, and every defect the run exposed in slop-mop itself.

Method

Every run follows the same five steps, and the last one is the one that matters.

  1. Pick a repository cold. No coordination with maintainers, no pre-cleaning, no discarding a run that goes badly.
  2. Record the starting board. sm scour before anything is touched, artifact committed.
  3. Run sm refit gate by gate. Fix what should be fixed. Where the honest move is to accept the existing state, baseline it and say so.
  4. Record the finishing board, and separate the fixes from the baselines in a table.
  5. File every piece of tool friction against ourselves as a barnacle, and publish the count. See below.

The reason step 5 exists: a green board proves nothing on its own. It can mean the repo was already in good shape, or that we disabled gates and lowered thresholds until the screen turned green — and those look identical from the outside. So every study carries a fixed-versus-baselined table, a suppression count, and the anti-gaming meta-gates left switched on.

Refit · one-time Onboarding, and what these studies document. The goal is a repo with no known issues and a committed baseline, so that afterwards anything flagged is new slop rather than years of accumulated noise.
Maintenance · every watch sm swab → sm scour → sm buff. The steady state, where the real code-quality work gets exercised. Not what these studies measure.

Barnacles · what each run cost us

A barnacle is friction in slop-mop itself — a false positive, a misleading message, a gate that fails for the wrong reason. We file them against our own repo and publish the count per run, because a tool that grades other people's code has no business hiding its own defect rate.

  • rulebook-ai · 10 barnacles · #331, #332
    The worst was a security scanner that never ran being reported as a finding: on a checkout without pip-audit, the gate announced “1 security scanner(s) found issues” — naming a vulnerability that did not exist while concealing that nothing had been audited. The guard for exactly that already existed in our code and was never called from anywhere.

    Also: a gate that could not tell code from prose, refit blaming the wrong gate, and two path bugs. All ten fixed. Our first attempt at fixing the scanner bug was worse than the bug, and review caught it.

  • OpenHands · 2 barnacles · #263, #264
    refit reformatted 94 applied database migrations — historical records that must never be rewritten — and separately re-formatted 417 files in a repo that already pinned its own formatter, which then disagreed and demanded the work be redone.

    Both fixed. The lower count here is not a better result: this run touched fewer gates deeply, so it had fewer chances to trip over us.

Twelve barnacles across two runs is a high rate, and we would rather state it than let it be discovered. It is what a young tool with limited support looks like when it meets a codebase it has never seen. The number we care about is whether it falls on the next run.

What these are for: to show what onboarding a real repository actually looks like, including the parts that make us look bad. If a run went badly we publish it anyway; if the tool broke something we name it and link the fix.
