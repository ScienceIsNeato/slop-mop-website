rulebook-ai, cold.

Running sm refit on a repo that had never heard of us, and publishing whatever fell out.

Case study #1 onboarded a 322k-line giant, and the honest answer there was mostly baselining. So we ran the opposite experiment: a small repo, picked from the wild, that had never heard of us — botingw/rulebook-ai, ~8.5k lines of Python. No coordination with the maintainer, no cherry-picking, nothing pre-cleaned. Run sm refit and publish whatever falls out.

Two crashes that were waiting to happen

The headline result is not the grade. It is that a type gate, on a repo nobody had type-checked end to end, surfaced two genuine latent crashes. Neither is a style complaint — both are exceptions waiting for the right input.

  • Crash 1 · Path / None
    Single-file assistant specs did target_path / spec.filename, but filename is declared Optional[str]. A spec that omitted it raised a bare TypeError deep inside the copy strategy, naming neither the spec nor the field.

    Fixed: the single-file branch now fails fast with a message naming the offending spec. The condition was unreachable only by luck of which specs shipped.

  • Crash 2 · the dict.get default that never fires
    entry.get("path", "").strip("/"). The default applies when the key is absent — not when it is present and null. A manifest with an explicit path: null returned None and blew up on .strip().

    Fixed: (entry.get("path") or ""). A one-character class of bug that no formatter and no linter was ever going to catch, and which reads as correct at a glance.

The gate was right about their CI

github-actions-hygiene opened with 23 findings, and one of them was not hygiene at all: the workflows still called actions/upload-artifact@v3, which GitHub retired. Their pipeline had been failing on that since September 2025 — visible on their Actions tab the whole time, and exactly the kind of thing that becomes invisible once a badge has been red long enough. Pinning the actions to SHAs and moving to v4 put their own CI back in business as a side effect of running our gate.

The same pass found grpcio==1.71.0 pinned exactly, which has no wheel for current Python and fails to compile from source, and a [tool.pytest] block whose addopts was a string where modern pytest requires a list — the test suite refused to start until that was fixed. Neither is glamorous. Both are the difference between a new contributor getting a working checkout and giving up.

What was actually fixed — versus baselined

Case study #1 earned a hard sentence: most of that PR was accepting the existing state. This one lands differently, and the numbers say so plainly.

Genuinely fixed Two latent crashes; 13 mypy errors; 18 pyright unknown-type errors resolved by giving yaml.safe_load a typed boundary rather than silencing it; 12 broken documentation links; a 111-line create_parser() split along the seams its own comments already marked; the retired CI action; the uninstallable pin; the config that stopped pytest booting; stubs declared for a dependency that was already required at runtime; and 25 new tests.
Suppressed 9 markers total. Seven are pragma: allowlist secret on the literal string "not-needed" — a placeholder API key in distributed template files, copied verbatim into seven packs. One # nosec, attached to a URL-scheme check that actually validates. One # noqa for reaching at a private argparse type. For contrast, case study #1 added 61.
Baselined Coverage, and only coverage. sm init wrote an 80% threshold; the repo measures 40%. Rather than gate on a bar it has never met, the threshold records where it actually stands and just-this-once requires ≥80% coverage on changed lines — so every future PR has to move the number up rather than sideways.
Scoped out The tool_starters and vscode-extension trees, excluded from six gates. These are template packs copied byte-for-byte into user projects, so the same file gets analysed once per copy — pyright reported 555 errors that were really 18, repeated. Excluding verbatim distribution copies is scoping, not hiding, but it is a judgement call and it belongs in this row.
Not compromised Strict typing was satisfied, not downgraded — strict_typing and pyright strict are both still true and both pass. The two anti-gaming meta-gates, gate-dodging and silenced-gates, are enabled and green, which is the machine-checkable version of this whole table.

The honest ledger · we broke their tests, then nearly hid it

The worst thing in this case study is ours, and it is worth more than the grade.

  • Our regression · a security fix that deleted a feature
    A bandit finding flagged urlopen on a URL from an environment variable. The obvious fix — restrict the scheme to http/https — quietly removed a supported workflow: pointing RULEBOOK_AI_INDEX_URL at a local file for offline use, which is also how their entire community-index integration suite builds its fixtures. Three of their tests went red because of us.

    Fix: file: belongs in the allowlist. The variable is operator-supplied configuration, not attacker-controlled input, and the allowlist still keeps urlopen away from schemes nobody intends. Satisfying a scanner is not the same as being correct.

  • Worse · the check that proved it was “pre-existing” was wrong
    We reported those three failures as pre-existing, on the strength of stashing our changes and re-running. But git stash only removes uncommitted work — the breaking change was already committed, so it survived the stash and every “baseline” run reproduced the failure. It looked convincingly like someone else’s problem.

    Fix: check out the actual merge-base in a throwaway worktree and run it there. All 56 of their tests pass at the merge-base — which made the regression, and the false alarm, ours. A wrong baseline does not produce an error message; it produces confidence.

  • Barnacle · a scanner that never ran, reported as a finding
    On a checkout whose environment lacked pip-audit, dependency-risk failed with “1 security scanner(s) found issues” and a single finding reading “pip-audit found issues” — naming a vulnerability that did not exist, while concealing that nothing had been audited at all. The guard for exactly this already existed in our codebase, with a comment describing exactly this failure. It was never called from anywhere.

    Fix: a scanner that fails to start is a broken environment, not a security finding. It now warns and names the install command. The first attempt at that fix was worse than the bug — it made a missing scanner render as “All security checks passed” — and review caught it before it shipped.

  • Barnacle · the gate that could not tell code from prose
    Python subscript-then-call is byte-identical to Markdown link syntax, so a documented handlers[cmd](args) inside a fenced code block was reported as a broken link to a file named after the argument. After we fixed 12 genuinely broken links, this false positive was the only thing standing between the gate and green.

    Fix: fenced blocks are skipped and inline code spans blanked. Review then found two more holes in that fix — multi-backtick spans and spans wrapping a line — both now covered by tests.

  • Barnacle · refit blamed the wrong gate
    A targeted scour runs the requested gate and its dependencies. When a dependency failed, refit still announced the gate it was iterating and pointed at that gate’s log — which had not been rewritten, so it showed the previous run’s output. We chased a stale 13-error type log while the real failure was a one-line formatting complaint.

    Fix: the failing gate and its log now come from the artifact’s own first_to_fix, which had been right the entire time.
